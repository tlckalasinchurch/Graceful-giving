# ส่วนที่ 1: ยกยอดเงินสด/ธนาคาร และกระทบยอดกับสมุดบัญชี

วันที่: 2026-10-30 · สถานะ: อนุมัติแล้ว (2026-10-30)
งานต่อเนื่อง: ส่วนที่ 2 (อนุมัติเบิกหลายคน) และส่วนที่ 3 (เชื่อมสลิป LINE) มีเอกสารของตัวเองภายหลัง

## เจตนาและเหตุผล

ปัจจุบันเหรัญญิกนับเงินถวายบนกระดาษ 2 แผ่น (แยกประเภท + รวมยอด/นับแบงก์-เหรียญ) หักค่าใช้จ่ายวันอาทิตย์ ยกยอดไปสัปดาห์ถัดไป แล้วบวกยอดโอนจากสลิปและเทียบกับสมุดบัญชีด้วยมือ ทำให้สับสน

หน้า "นับเงินถวาย" (`client/src/pages/CountingDetail.tsx`, router `counting`) ทำส่วนนับ/แยกประเภท/หักค่าใช้จ่าย/รายการธนาคารได้แล้ว แต่ใช้กับวิธีทำงานจริงไม่ได้ เพราะ:

1. บังคับกฎ "ถวายเงินสด − หักเบิก = นำฝาก" (`checkDepositIdentity`, `expectedDeposit`/`depositVariance` ใน `shared/counting.ts`) คือต้องฝากเงินสดที่เหลือทั้งหมด แต่โบสถ์เลือกได้ทุกสัปดาห์ว่าจะเก็บไว้หรือฝาก และบางสัปดาห์ต้องถอนจากธนาคารมาจ่าย
2. ไม่มียอดยกมา/ยกไป
3. จับคู่สมุดบัญชีได้ทีละรายการ (`passbookMatched`) แต่ไม่มีการเทียบยอดคงเหลือ

ผู้ใช้ยืนยันว่ากฎเดิมเปลี่ยนได้เลย (ไม่ใช่ข้อกำหนดของผู้ตรวจบัญชี)

## เป้าหมาย

- เงินแยกเป็น 2 กระเป๋า: **เงินสดในมือ** และ **บัญชีธนาคาร** แต่ละกระเป๋ามียอดยกมา → ยกไป ต่อเนื่องทุกรอบ
- ยอดยกมาของรอบใหม่ = ยอดยกไปของรอบก่อน โดยอัตโนมัติ
- รองรับทุกสัปดาห์: เก็บเงินสดไว้, ฝากบางส่วน/ทั้งหมด, ถอนจากธนาคารมาจ่าย
- ตรวจได้ 2 ตัวเลขต่อรอบ: เงินสดในมือตรงกับที่นับได้จริง และยอดธนาคารตรงกับสมุดบัญชี (เมื่อกรอก)

## ไม่ทำ (ในส่วนนี้)

- ไม่สร้างสมุดเงินสด/สมุดธนาคารแยกเป็นระบบใหม่ (แนวทาง ข ที่ตัดทิ้ง)
- ไม่ทำขั้นตอนอนุมัติการถอน — ส่วนที่ 2 (ส่วนนี้แค่บันทึกยอดถอน)
- ไม่ดึงสลิปจาก LINE — ส่วนที่ 3 (ยอดโอนยังกรอกเองแบบเดิม)
- ไม่บังคับให้ฝากเงินทุกสัปดาห์

## ต่อต้าน (ถ้าเกิด ถือว่าล้มเหลวแม้ทำงานได้)

- ใช้ยากกว่ากระดาษ: เพิ่มช่องกรอกได้เฉพาะที่จำเป็น
- ยอดยกมาเปลี่ยนเองเงียบๆ หลังลงบัญชีแล้ว จนตรวจย้อนหลังไม่ได้
- ปิดรอบได้ทั้งที่เงินสดในมือไม่ตรง โดยไม่มีคำอธิบาย

## ข้อจำกัด

- เงินคำนวณเป็นสตางค์ (`toSatang`/`sumSatang`) ห้ามบวกทศนิยมตรงๆ (มีเหรียญ 25/50 สตางค์)
- เปลี่ยน schema ใน `drizzle/schema.ts` → `pnpm db:push` และต้องแก้ `server/schema_init.ts` ให้ตรงกัน (DDL แบบ idempotent ที่ `getDb()` รันตอนเชื่อมต่อ)
- ทุก query ผูก `churchId`; การเปลี่ยนแปลงสำคัญต้องเขียน audit log แบบเดียวกับ procedure อื่นใน `counting`
- รอบที่มีอยู่แล้วใน production (สร้างก่อนฟีเจอร์นี้) ต้องเปิดดูได้ไม่พัง

## แนวทางที่พิจารณา

| แนวทาง | สิ่งที่ได้ | สิ่งที่เสีย |
|---|---|---|
| **ก. ต่อยอดหน้านับเงินถวาย** (เลือก) | ใช้ของเดิมเกือบทั้งหมด คนใช้เห็นหน้าเดียว | เงินเข้าออกกลางสัปดาห์ต้องบันทึกในรอบของสัปดาห์นั้น |
| ข. สร้างสมุดเงินสด/ธนาคารแยก | ยืดหยุ่นที่สุด | งานใหญ่หลายเท่า ขัดเป้า "ไม่ซับซ้อน" |
| ค. เพิ่มแค่ช่องยกยอด | เร็ว | ยังพิมพ์ซ้ำ และการอนุมัติไม่ตรงเงื่อนไขธนาคาร |

ผู้ใช้เลือก **ก** และลำดับงาน 1 → 2 → 3

## สูตร (ตัดสินร่วมกับผู้ใช้)

```
กระเป๋าเงินสด
  เงินสดยกมา + ถวายเงินสด(นับได้) + ถอนจากธนาคาร − หักค่าใช้จ่าย − นำฝาก
  = เงินสดยกไป (คำนวณ)

กระเป๋าธนาคาร
  ยอดธนาคารยกมา + โอนเข้า + นำฝาก + เข้าอื่นๆ − ถอน − ออกอื่นๆ
  = ยอดธนาคารยกไป (คำนวณ)  ⟷  เทียบ "ยอดล่าสุดในสมุดบัญชี" (ถ้ากรอก)
```

ตรวจรายการในสมุดบัญชีทีละรายการด้วย `passbookMatched` ที่มีอยู่แล้ว

## การออกแบบ

### ข้อมูล (`drizzle/schema.ts` + `server/schema_init.ts`)

`counting_sessions` เพิ่ม (decimal 15,2 ทั้งหมด, nullable):
- `openingCash`, `openingBank` — ยอดยกมา บันทึกค้างไว้ตอนลงบัญชี (ไม่คำนวณสดทุกครั้ง)
- `closingBank` — ยอดธนาคารยกไป บันทึกค้างไว้ตอนลงบัญชี เพื่อให้รอบถัดไปอ่านยอดยกมาได้โดยไม่ต้องคำนวณรอบก่อนใหม่ (ยอดเงินสดยกไปคือ `cashOnHandActual`)
- `cashOnHandActual` — เงินสดที่เหลืออยู่จริงหลังฝาก/จ่ายแล้ว (นับกล่องเงินจริง)
- `passbookBalance`, `passbookBalanceDate` — ยอดล่าสุดในสมุดบัญชีและวันที่ของยอดนั้น

`bank_record_type` enum เพิ่ม: `withdrawal` (ถอนจากธนาคารเข้ากระเป๋าเงินสด), `other_in`, `other_out` (ค่าธรรมเนียม ดอกเบี้ย โอนจ่ายบิล — ใช้ `notes` อธิบาย)

### คำนวณ (`shared/counting.ts`)

- `reconcile()` รับ `openingCash`, `openingBank`, `cashOnHandActual`, `passbookBalance` เพิ่ม และคืน:
  `closingCashExpected`, `cashOnHandVariance` (= actual − expected), `closingBankExpected`, `passbookVariance` (null ถ้าไม่ได้กรอก), `withdrawalTotal`, `otherInTotal`, `otherOutTotal`
- ลบ `expectedDeposit`, `depositVariance`, `checkDepositIdentity` และแก้ comment "invariant the church audits against" ให้เป็นสูตรกระเป๋าเงินสด
- `isBalanced` = `cashVariance` = 0 และ `transferVariance` = 0 และ `cashOnHandVariance` = 0
- `passbookVariance` แสดงผลอย่างเดียว ไม่นับใน `isBalanced` และไม่บล็อกการลงบัญชี (ดูข้อ 6 ใน "เรื่องที่ผมตัดสินเอง")
- `cashVariance` (นับได้ vs ซองเงินสด) และ `transferVariance` คงเดิม

### ยอดยกมา

- ตอนลงบัญชี (`post`) ระบบหา **รอบก่อนหน้า** = รอบที่ `serviceDate` ล่าสุดก่อนรอบนี้ซึ่งสถานะ `posted`/`closed` แล้ว ใช้ยอดยกไปของรอบนั้น (`cashOnHandActual` สำหรับเงินสด, `closingBankExpected` สำหรับธนาคาร) แล้วบันทึกลง `openingCash`/`openingBank` ของรอบนี้
- ระหว่างนับ (ยังไม่ลงบัญชี) หน้าจอแสดงยอดยกมาแบบคำนวณสดจากกฎเดียวกัน
- **ห้ามลงบัญชีข้ามรอบ**: ถ้ามีรอบที่ `serviceDate` เก่ากว่ายังไม่ `posted` → `post` ตอบ `CONFLICT` พร้อมบอกว่าต้องลงบัญชีรอบไหนก่อน
- **รอบแรกสุด** (ไม่มีรอบก่อนหน้าที่มียอดยกไป): ฝ่ายการเงิน (`financeProcedure`) กรอกยอดยกมาเองได้ครั้งเดียวผ่าน procedure ใหม่ `counting.setOpeningBalances` บันทึก audit log

### ปิดรอบ

- `post` ต้องมี `cashOnHandActual` เสมอ (ถ้าไม่มี → `BAD_REQUEST`)
- ถ้า `isBalanced` = false ใช้กติกาเดิม: ต้องมี `varianceNote` ก่อนลงบัญชี
- `postCountingSession` (`server/db.ts`) เขียนรายการถวายและค่าใช้จ่ายลงบัญชีเหมือนเดิม รายการ `withdrawal`/`other_in`/`other_out` **ไม่** เขียนลงบัญชีรายรับรายจ่าย (ดู "เรื่องที่ผมตัดสินเอง")

### หน้าจอ (`client/src/pages/CountingDetail/components/`)

- `BankRecordsTab`: เลือกประเภทใหม่ (ถอน / เข้าอื่นๆ / ออกอื่นๆ) ใช้ฟอร์มเดิม
- `ReconciliationSummaryTab`: แทนกล่อง "ยอดที่ควรนำฝาก" ด้วย 2 กล่องตามสูตรด้านบน แต่ละบรรทัดแสดงตัวเลข + ช่องกรอก `cashOnHandActual` และ `passbookBalance`/วันที่ แสดงส่วนต่างเป็นสีเมื่อไม่ตรง และจำนวนรายการธนาคารที่ยังไม่ติ๊กสมุดบัญชี
- รอบแรกสุด: แสดงฟอร์มกรอกยอดยกมา (เฉพาะฝ่ายการเงิน)
- ใช้คอมโพเนนต์ใน `client/src/components/ui/` และ `fmtBaht` เดิม

### รอบเก่าที่มีอยู่แล้ว

รอบที่ `openingCash` เป็น null และลงบัญชีไปแล้ว: เปิดดูได้ ส่วนกระเป๋าเงินสด/ธนาคารแสดง "รอบนี้สร้างก่อนมีการยกยอด" ไม่คำนวณส่วนต่าง และไม่นับเป็นรอบก่อนหน้าสำหรับยอดยกมา (รอบใหม่รอบแรกจึงเข้าเงื่อนไข "รอบแรกสุด")

### ทดสอบ

## เรื่องที่ผมตัดสินเอง (ผู้ใช้ยังไม่ได้ยืนยัน)

1. **นับกล่องเงินสดจริงตอนปิดรอบ (`cashOnHandActual`) เป็นข้อบังคับ** เพราะไม่อย่างนั้นยอดยกไปเป็นแค่ตัวเลขคำนวณที่ไม่เคยถูกตรวจ ซึ่งเป็นจุดที่ความผิดพลาดสะสมข้ามสัปดาห์
2. **ยอดยกมาบันทึกค้างไว้ตอนลงบัญชี** แทนคำนวณสด เพื่อให้รอบที่ปิดแล้วไม่เปลี่ยนตามการแก้ไขรอบอื่น
3. **ห้ามลงบัญชีข้ามรอบ** เพื่อให้สายยอดยกมาต่อเนื่อง
4. **ค่าธรรมเนียม/ดอกเบี้ย/โอนจ่ายบิล (`other_in`/`other_out`) ไม่ลงบัญชีรายรับรายจ่าย** ในส่วนนี้ เพราะบิลบางรายการอาจถูกบันทึกในหน้า "รายจ่าย" อยู่แล้ว ถ้าลงซ้ำยอดจะเกิน
5. ยอดธนาคารยกไปใช้ยอดคำนวณเสมอ ยอดในสมุดบัญชีใช้เทียบเท่านั้น เพราะวันที่อัปเดตสมุดอาจไม่ตรงกับรอบ ถ้านำมายกยอดจะดึงรายการของรอบอื่นเข้ามาปน

6. **ส่วนต่างกับสมุดบัญชีแสดงอย่างเดียว ไม่บล็อกการลงบัญชี** เพราะผู้ใช้ยังไม่ได้บอกว่าอัปเดตสมุดบ่อยแค่ไหน ถ้าอัปเดตห่างหลายสัปดาห์ ยอดในสมุดจะรวมหลายรอบและต่างจากยอดของรอบเสมอ ถ้าภายหลังยืนยันว่าอัปเดตทุกสัปดาห์ เปลี่ยนให้นับใน `isBalanced` ได้
