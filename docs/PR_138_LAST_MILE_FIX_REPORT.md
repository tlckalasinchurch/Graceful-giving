## 3. CSV BOM verification

- Cause: the server adds `\uFEFF` to the offerings, expenses, and transactions CSV. `Transactions.tsx` added a second one. Offerings and Expenses did not. The Reports server does not add one, and its page adds one.
- Fix: all four pages call `toCsvBlob()`. It removes leading BOMs and adds one.
- Byte tests (`csvDownload.test.ts`):
  - Input without a BOM: bytes 0 to 2 are `EF BB BF` and bytes 3 to 5 are not.
  - Input with one BOM: same result.
  - Input with two BOMs: the file has exactly one `EF BB BF` sequence.
  - Thai text: the header "ID,วันที่,รายการ" contains `E0 B8 A7` ("ว") and decodes back to the original string.
  - `Blob.size` equals the byte length.
  - A source guard test fails if a page has `new Blob(` or its own `\uFEFF`. I checked that this test fails on the old `Transactions.tsx` and passes on the fix.
- Server test: the offerings, expenses, and transactions exports each start with exactly one BOM (byte level).
- Excel and Thai: the BOM stays and the text stays UTF-8. I did not open the file in Excel.

## 4. Thailand date verification

### 4.1 How dates are stored (evidence)

- Financial date columns (`receiptDate`, `expenseDate`, `serviceDate`, `requestDate`, `approvalDate`, `disbursedAt`) are `timestamp` without time zone (`drizzle/schema.ts`).
- drizzle-orm 0.44.6 writes `value.toISOString()` (UTC) and reads `value + "+0000"` (`pg-core/columns/timestamp.js`).
- The test `storage semantics` uses the same Drizzle version on an embedded PostgreSQL (PGlite). It writes 00:00 Bangkok on 2026-11-01. The database holds `2026-10-31 17:00:00`. Drizzle returns the same instant.
- Result: a column holds the UTC wall clock of the instant. The correct calendar date is the Bangkok date of that instant. The old code used the UTC date and was wrong from 00:00 to 06:59 Bangkok time. The storage meaning is clear, so the fix needs no schema change.

### 4.2 Date paths

| Path                            | Value written                                                                              | CSV date before                       | CSV date now |
| ------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------- | ------------ |
| Manual offering (`NewOffering`) | Chosen date at 12:00 browser time (05:00 UTC in Bangkok)                                   | Correct                               | Correct      |
| Expense (`NewExpense`)          | Same, 12:00 browser time                                                                   | Correct                               | Correct      |
| Counting posting                | `serviceDate` from a date input, `new Date("YYYY-MM-DD")` = 00:00 UTC = 07:00 Bangkok      | Correct                               | Correct      |
| Giving Station and LINE slip    | `receiptDate` = given date, slip date, declared date, or `new Date()` (a real time of day) | **Wrong from 00:00 to 06:59 Bangkok** | Correct      |
| Withdrawal dates                | `new Date()`                                                                               | Not in a CSV                          | Not in a CSV |

- App display: `formatThaiDate` and `toLocalISODate` use the browser time zone. For a browser in `Asia/Bangkok` this equals the CSV date. A test sets the process zone to `Asia/Bangkok` and compares the two for all seven instants.
- A person who enters a manual date from a browser outside Thailand gets a different stored instant (noon in that zone). This is outside this task.

### 4.4 Findings that I did not change

1. **Database default `now()`.** In PGlite with the session zone set to `Asia/Bangkok`, `defaultNow()` stored `23:20` for an instant that is `16:20` UTC. If the production database session zone is not UTC, rows that use the default are stored 7 hours late and the Bangkok date would be wrong. Most code writes explicit `Date` values, so the effect is limited. Confirm that the production session zone is UTC. I could not check production.
2. **`bangkokDate()` in `server/db.ts` (withdrawal-to-counting-round link).** The helper is `(<timestamp column> AT TIME ZONE 'Asia/Bangkok')::date`. For a `timestamp` column this reads the stored value as Bangkok local time. The column holds UTC. On PGlite with a UTC session, stored `2026-11-01 00:00:00` (Sunday 07:00 Bangkok) gives `2026-10-31`. Stored `2026-10-31 17:00:00` also gives `2026-10-31`. The correct values are `2026-11-01`. The helper is off by 14 hours. A payout made on a Sunday after about 14:00 Bangkok time can match the next counting round and not that Sunday's round. The tests for this logic (`withdrawals.workflow`) are in the skipped PostgreSQL group, so no test caught it. This is financial logic. The task forbids changing it. **Decision for the owner.** The smallest fix is `(<column> AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Bangkok')::date`. Run it on a test database first. Rerun the skipped suite with it.
3. **Reports and dashboards by month.** Other SQL (`extract(month …)`, month ranges) groups by the stored UTC value. A record from 00:00 to 06:59 on the first day of a month can fall in the previous month in those reports. I did not change them. The CSV rows of the reports export now use the Bangkok date.
4. **Download file names** use the UTC date of "now". Before 07:00 Bangkok time the name has the previous day. This is cosmetic.

## 5. Export size limit

- Path: the page calls a tRPC query. The server builds the whole CSV as one string and returns it in the JSON response. Vercel rejects a function response above 4.5 MB.
- Before: an over-size export reached the browser as a gateway error. The pages showed a generic message or raw English text.
- Now:
  - After the CSV is built, the server measures the JSON-encoded size in UTF-8 bytes. If it is above 4,000,000 bytes, the server throws `PAYLOAD_TOO_LARGE` with this Thai message: "ข้อมูลที่ส่งออกมีขนาดใหญ่เกินที่ระบบรองรับ กรุณาเลือกช่วงวันที่ให้แคบลง แล้วส่งออกใหม่ทีละช่วง".
  - The pages show it in the error toast. A gateway failure with no tRPC code (`FUNCTION_PAYLOAD_TOO_LARGE`, `413`, "is not valid JSON") gets the same message.
  - The export never returns part of the data. Tests: a 1,700-row export with long notes fails whole. A 500-row export keeps all 500 rows.
  - The inputs and filters (date range, fund, category, search, type) are not changed.
- The limit counts Thai text at 3 bytes per character and counts JSON escapes. A test checks both.
- Documented limitation that remains: all rows are held in memory and one response carries the file. There is no streaming. About 15,000 rows is the practical size. The 4,000,000-byte value is a conservative choice. It was not measured against a real Vercel response.
